**Server** (`crates/icarus-server`, binary `icarus-server`):
- Local socket server: length-prefixed JSON frames, token auth, one server per state directory, a protocol version in the hello.
- Terminals:
  - PTYs owned by the server, with a headless `alacritty_terminal` emulator per session.
  - Rendered-screen and scrollback reads; snapshots replay as VT sequences.
  - Reattach resumes by sequence number, or falls back to a snapshot.
  - Terminal queries (DSR, DA) are answered by the server.
- Agents:

  - Clients attach, detach and resume by sequence number while the agent keeps working.
  - Usage meters come from Claude Code's own `rate_limit_event`; no credentials are read.
  - Sessions survive a server restart: they come back asleep and resume the provider session (`--resume`) on the next message. Shutting the server down puts agents to sleep instead of killing them.
  - Interrupt, sleep and kill are supported.
- Projects and workspaces (SQLite `state.db`):
  - Adding a project detects its root, canonical remote and default base.
  - Creating a workspace makes a git worktree under the Icarus workspace root with a DNS-safe slug (D3), and starts its agent at once ("always an agent").

- A fake stream-JSON agent (`icarus-fake-agent`) lets tests run without Claude or the network.
- **Codex provider** (`--provider codex`, or `agents.default: "codex"`):

  - Sleep, wake and restart restore resume the Codex thread id. Auth is the user's own `codex login`; Icarus never reads its tokens.
  - The binary comes from `agents.commands.codex`, else `ICARUS_CODEX_BIN`, else `codex` on `PATH`. A fake app-server (`icarus-fake-codex`) backs the end-to-end tests.

**Remote servers:**
- `icarus-server serve --listen <ip:port>` (repeatable, or the `server.listen` setting) accepts clients over TLS next to the local socket. The certificate is self-signed and stays in the server's state directory.
- It only binds loopback, private and Tailscale addresses unless `--allow-public` is given, and the error says why.
- `icarus server pair` prints a one-time code: 8 characters, single use, valid 10 minutes. Failed attempts are rate-limited per address. A client trades the code for its own token, which is stored hashed in `state.db`.
- `icarus server clients` lists paired clients, and `icarus server revoke <id>` drops one and closes its live connections. These, and `pair`, only work on the server's own machine.
- `icarus remote add <name> <addr> --code <code>` pairs, pins the certificate fingerprint and saves the server in `~/.config/icarus/servers.json`. `ssh://host` servers can be saved too. `remote list|remove` manage the list, and `--server <name>` points any command at a saved server.
- The local socket and its token work as before, and the protocol only gained optional fields.
- Checked live over Tailscale between two Macs: pairing with a pinned certificate, `--server` commands, a terminal run on the remote machine with its output read back, and `server pair` refused from the paired client.

**Notifications (server, D7):**
- The server makes notifications and keeps them in `state.db` (the newest 500), so none are lost while no client is connected. Each has an id, kind, title, body, workspace, time and a read flag.
- Kinds: an agent finished its turn, waits for input or a permission, or failed (a failed turn, or a process that died on its own); CI failed, a review was requested, a PR merged (from the rules' GitHub poll, dry runs included); and the rules' `notify` action.
- Every kind can be switched off with `notifications.<kind>`, plus `notifications.enabled` and `notifications.sound`. All default to on.
- Repeats are dropped: agent news within 5 seconds (Orca's cooldown), a rule's message within 10 minutes, and GitHub news once per state (the same PR head, the same merge).
- Clients get a `notification` event (with `sound`) and `notifications.changed` with the unread count. RPCs: `notification.list|read|clear|kinds`. CLI: `icarus notifications [--unread] [--json]`, `icarus notifications read <id>|--all`, `icarus notifications clear`.

**Session history and sleep/wake (server, D8):**
- `agent.history` lists past sessions (sleeping, exited or killed, with at least one turn): title, provider, workspace, account, first prompt, last activity, turns and whether they can be resumed. It filters by workspace, pages with `before`, and searches what you asked and what the agent answered (every word must appear; a snippet shows where). The index is in memory and reads only the new part of each log.
- `agent.resume` brings a past session back as a live agent in its own directory, through the provider's own resume. Killed sessions no longer come back by themselves after a server restart; they stay in history until resumed.
- `workspace.sleep` puts the workspace's agents to sleep and stops its terminals' processes; screens and scrollback stay. `workspace.wake` restarts exactly what was parked. Cards show `sleeping`.
- CLI: `icarus agent history [--workspace] [--search]`, `icarus agent resume <id>`, `icarus workspace sleep|wake <id>`.

**Review mode (server)** (github-review.md, D23):

Drafts are keyed by PR, never by commit, so they survive server restarts and pushes. A file comment keeps its kind on disk (the fork lost it).
- A draft on lines outside the PR's diff becomes a file comment that quotes the code, as in the fork; a file the PR does not touch is refused with a reason. Up to 200 drafts are kept.
- `review.submit` sends one GitHub review with every draft (GraphQL variables, not a string-built query). On success the drafts and summary clear; on failure they stay and GitHub's message comes back word for word. After a rebase or a merge of the target, the reviewed version is replayed onto the new base (`refs/icarus/review-base/…`), so the Changes list shows only what changed since your review. **Terminals survive restarts:**
- `icarus server restart`, `icarus update install` and a SIGTERM from launchd or systemd hand terminals to the next server. Processes, pids, background jobs, scrollback and sequence numbers stay the same, so attached clients resume by sequence. Agents still sleep and resume.
- How it works: the stopping server stops its readers and passes each PTY master over `SCM_RIGHTS` to a small `icarus-server hold` process, with the screen snapshot, recent output and the auth token. The next server takes them over on start. The master is never closed, and children run in their own sessions, so they get no SIGHUP. A holder that nobody claims gives up after 2 minutes (`ICARUS_HANDOFF_HOLD_SECS`).
- `icarus server stop` still ends terminals. After a crash or `kill -9`, the PTYs close with the server and their shells get SIGHUP; anything detached (`nohup`, `setsid`) is orphaned. The next server lists these terminals as `lost` (from `terminals.json`), and they can be respawned.
- Tested end to end (`crates/icarus-cli/tests/restart_e2e.rs`) on macOS and in a Linux container. The launchd and systemd restart paths have not been tested against a real service.

**App terminals run on the server (§3c, features §2.5/§4):**
- `icarus terminal attach <id>` (or `--create [--cwd] [--workspace] [--label] [-- cmd…]`) shows a server terminal in the current one, dtach-style: raw mode, the screen replayed, then output streamed by sequence; keys go to `terminal.write`, size changes to `terminal.resize`. It rides out a server restart (reconnects for up to 60 s and resumes by sequence, with no gaps or repeats) and exits with the shell's code (unknown, so 0, for a shell adopted across a restart). Closing the viewer leaves the shell running.
- In the app, every new local shell in an Icarus workspace (terminal panel, centre terminals, layout terminal tabs) is created on the server for that workspace and shown by running `icarus terminal attach` (the `icarus` next to the app in a release bundle, else on `PATH`). The tab keeps the server id, so a restored tab reattaches to the same shell; if that shell is gone a new one starts. **Language tooling and themes on import (§3b, D10, D28):**

Keys the user already set are kept and listed, comments and trailing commas are read, and the commented original is saved once as `settings.json.before-icarus-import`. `--dry-run` writes nothing, `--print-zed` prints the Zed settings, `--skip-zed` leaves Zed alone.

**Import from Zed:**
- `icarus settings import-zed [--from DIR] [--from-data DIR] [--zed-dir DIR] [--dry-run] [--json]` brings a normal Zed install (`~/.config/zed`; extensions from Zed's data directory, `~/Library/Application Support/Zed` or `~/.local/share/zed`) into the app's config directory (`~/.config/icarus`). `ICARUS_ZED_SOURCE_DIR` / `ICARUS_ZED_SOURCE_DATA_DIR` override the source.

**Notes (server):**
- Notes live in state.db: a note sits on a file and line range of a workspace (worktree-relative path, optional `side: old` for the base side of a diff, optional `base`), with its author (`user` or `agent` plus the agent's id), markdown body, the lines it was written on, times and a resolved flag. Each note has a thread of replies by `user`, `agent` or `reply-agent`; a reply-agent entry also carries its session id, status (pending, running, done, failed), error and the files it changed.
- RPCs: `note.add {workspace | cwd, path, line, end_line?, body, author?, agent_id?, side?, base?}`, `note.list {workspace | cwd, path?, include_resolved?}`, `note.get`, `note.thread` (the conversation as text), `note.reply {id, body}`, `note.edit {id, body, reply_id?}`, `note.remove {id, reply_id?}`, `note.resolve` / `note.unresolve`, and `attach.note {id}`. Every change broadcasts `note.changed {workspace, id, path, removed}`.
- Replying never messages the workspace's running agent. Each user reply starts its own throwaway session in the worktree (default provider and account, like other new sessions), given the whole thread: the note, file and lines with the current code, and every finished reply. Its last message is posted back as the reply; then the session is killed and dropped from the live agents, and its transcript stays in session history under the workspace. It may edit files when asked: the worktree is snapshotted before and after (the turn-snapshot code, which leaves the user's index alone), and the changed files are stored on the reply and listed under its answer. Several replies can run at once, each seeing the thread up to its own message. Failures keep the agent's error; `notes.reply_timeout_ms` (default 10 minutes) stops a session that takes too long; a server restart marks unfinished replies failed and kills their sessions. Reply sessions are not workspace agents (so layouts, rules and the agent list ignore them) and send no "agent finished" notifications.
- `attach.note` puts the whole conversation, with file, lines and code, in the composer as one `note` attachment, like PR review threads.
- CLI: `icarus notes add <path>:<line>[-<end>] <body…>`, `list [--path] [--all]`, `show`, `reply <id> <body…> [--wait]`, `edit`, `rm`, `resolve`, `unresolve`, `attach`, with `--json`. The workspace comes from `--workspace`, else `ICARUS_WORKSPACE_ID`, else the current directory; paths are relative to the current directory or the worktree; a literal `\n` in a body is a newline. Run by an agent (`ICARUS_AGENT_ID` set), the note or reply is authored by that agent, and an agent's reply starts no session.

**Source Control actions and agent turns** (source-control.md §1.6, §4; features §2.9):
- Server RPCs, so the app, the CLI and agents share them (they run where the worktree is): `git.status`, `git.discard`, `git.discard_kind`, `git.stage`, `git.unstage`, `git.commit {message, amend?, all?}`, `git.push {force_with_lease?}`, `git.pull`, `git.sync`. Every change broadcasts `git.changed {workspace, op}`. Errors are git's own words; git never waits on a prompt or an editor.
- Discard throws away only the uncommitted change (committed branch changes stay): edits go back to HEAD, untracked or newly added files are deleted, a file deleted on disk is restored, and a staged rename brings its old path back. Paths outside the worktree are refused.
- Commit takes what's staged, or every change when nothing is (the upstream commit box's rule); `--amend` without a message keeps the old one; commit hooks run and their output is the error.
- Push publishes a branch whose upstream isn't a same-named branch (a workspace branch starts out tracking its base, e.g. `origin/main`, which `published: false` reports); pull and sync refuse or skip until then. `--force-with-lease` refuses when the remote moved since the last fetch.
- CLI: `icarus git status|discard|stage|unstage|commit|push|pull|sync`, workspace from `--workspace`, `ICARUS_WORKSPACE_ID` or the current directory.
- App, Source Control panel: a hover Discard button per row ("Discard changes", "Delete untracked file", "Restore file"), only for an unstaged or untracked, non-conflicted change and never under a turn or commit scope, after a confirmation; an Agent turns section (prompt, `agent · 3m ago · N files +I −D`, click to scope the list to that turn, "Latest turn" only while no newer turn exists); a slim git bar with the branch, ↑ahead ↓behind or "not published", Commit…, Pull, Push and a menu with Sync and Force push (with lease), git errors shown verbatim. The commit box itself stays out of the panel as Orca removed it (§4): Commit… opens a small dialog where ⌘Enter commits, with an amend toggle. Actions: `icarus::CommitChanges`, `PushBranch`, `ForcePushWithLease`, `PullBranch`, `SyncBranch`, `DiscardSelectedChange`. Panels refresh at once on `git.changed`.
- Checked live: a tiny real-Claude turn appeared in Agent turns, a CLI commit and a CLI discard updated the open panel, and discarding a committed-only file was refused.

With `wait-for-setup` the workspace's agent exists at once but its first prompt (and a rules-created review agent) waits until setup ends. An `ask` project refuses a create without a decision (nothing is created); the rules' review workspaces answer it with run.

Cards show "Setting up" with a spinner, or "Setup failed" with the reason in a tooltip. Server terminals with a label (Setup, quick commands) are titled by it.

**New workspace: pull requests, cancel, trust, `orca.yaml` leftovers** (features.md §2.1):
- **From a pull request:** `workspace.create { pr }` takes a number, `#n` or a PR URL (a URL for another repository is refused). The server looks the PR up through `gh` (the user's login), fetches `refs/pull/<n>/head` from `origin` into `refs/icarus/pull/<n>` (so fork PRs work too), and creates the worktree on a branch named after the PR's head branch, so the card finds the PR; a same-repository PR's branch tracks `origin/<head>`. The workspace's base is `origin/<base branch>`, its title the PR's title, its `pull_request` the PR, and the name defaults to the head branch. CLI `icarus workspace create --from-pr <n|url>`; the dialog has a "Pull request" start point.
- **Cancel:** `workspace.create { create_id }` can be stopped with `workspace.create_cancel { create_id }`. The Linear and GitHub lookups, fetches, `git worktree add` and the shared-path copies run as killable child processes; a cancel kills them, removes the half-made worktree and the branch if the create made it, and the create answers `cancelled`. The server now runs `workspace.create` off the connection's request loop, so a cancel (or anything else) on the same connection isn't stuck behind a slow fetch. A failed create cleans up the same way. The dialog's button turns into "Cancel Create" (Escape too) while creating; Ctrl-C in `icarus workspace create` cancels.
- **Trust prompt:** a repository's committed scripts (the shared `scripts.setup` / `scripts.archive` from `orca.yaml` or the committed `icarus.json`, and `defaultTabs` commands) run only once the user trusts that exact content; trust is stored per project as SHA-256 digests (per script kind), so a change asks again. Local scripts (`icarus.local.json`, user settings) need no trust. An untrusted setup refuses the create before anything exists (`untrusted_scripts`, naming `icarus project scripts <id>` and `icarus project trust <id>`) unless it's skipped or the create passes `trust`; a branch whose `orca.yaml` setup differs from the trusted one is created but its setup is marked failed with that reason (`icarus workspace setup <ws> --trust` runs it). The rules' unattended review workspaces never run untrusted scripts. An untrusted archive script is skipped (the removal goes ahead, `archive.skipped` says why), as declining Orca's prompt does. New RPCs `project.scripts`, `project.trust` (optionally a workspace's checkout too) and `project.untrust`; CLI `icarus project scripts|trust|untrust <id>`, `workspace create --trust`. In the dialog, Create on an untrusted project shows the scripts with Trust and Create / Create without running them / Back (Enter doesn't answer it).
- **`ask` setup policy in the dialog:** a project whose `setupRunPolicy` is `ask` gets a "Setup script: Run setup / Skip" row.
- **`defaultTabs`:** `orca.yaml`'s `defaultTabs` (title, command) become server terminals, titled by the tab's title, added after the first pane's tabs of the layout a new workspace opens with (only when it opens with one, as Orca applies them on first activation). Commands run (then the shell stays) only when trusted; otherwise the tabs open as plain shells. Tab colours aren't kept.
- **`worktree.sharedDirectories` and `.worktreeinclude`:** read from the project root as Orca does, limited to existing gitignored paths (safe repo-relative paths only). Shared directories are symlinked to the root's, as in Orca (one install serves every worktree; Orca refuses to clone them); `.worktreeinclude` paths are private copies, as APFS clones (`cp -c`) on macOS and reflinks (`cp --reflink=auto`) on Linux, falling back to a plain copy. Problems are warnings on the create (`warnings`), never failures. Removing a workspace unlinks the shared links first, so they don't make the checkout look dirty, and puts them back if the removal is refused.
- Tests: `crates/icarus-server/tests/create_e2e.rs` (PR start point, cancel over the same connection, trust and re-trust, a branch with a different setup, shared paths), `crates/icarus-cli/tests/create_e2e.rs` (`--from-pr`, the trust error and `--trust`), unit tests for the parsing and digests, GPUI tests for the PR start point, the trust prompt and `ask` choice, and cancelling.

**SSH remote projects in releases:** Zed's SSH remoting runs a `remote_server` binary on the host, and a stable build used to download Zed's official one (built from upstream) from zed.dev. Icarus now ships its own:
- **Download, not bundled:** release builds (stable and preview channels) fetch `https://github.com/frbarbre/icarus/releases/download/v<icarus version>/icarus-remote-server-<icarus version>-<os>-<arch>.gz`, first with `curl` on the host and else through the app, which uploads it; both cache as Zed does. One hook in `auto_update`'s `get_release_asset` (`icarus_remote_server_asset`); nightly and dev keep upstream's path. Bundling every target in the app would add ~130 MB to each download for a feature most people won't use, and would still need an upload path per host.
- **Named after the Icarus release on the host** (`~/.icarus_server/zed-remote-server-stable-<icarus version>`), so an Icarus upgrade replaces the server even when the Zed base (1.30.0) stays; the server's own cleanup of older binaries compares Icarus versions too.
- **Built by the release:** `.github/workflows/release-remote-server.yml` (called by `release.yml`) builds static musl Linux x86_64 and aarch64 servers on native runners, as Zed does, plus macOS aarch64 and x86_64, in Zed's separate `--package remote_server` invocation with `.cargo/bundle-config.toml`. Publishing (`release.yml` and `release-publish.yml`) refuses to go ahead without all four. Windows hosts have no server yet. A trial run built all four without publishing.
- **Dev builds** build the fork's server from source and upload it by default (debug only; needs `cmake` on the app's PATH, since `wasmtime-c-api-impl` uses it). `ZED_COPY_REMOTE_SERVER=<path>` uploads a server you built (`cd app && cargo build -p remote_server --features debug-embed --target-dir target/remote_server --target aarch64-apple-darwin`), and `ZED_BUILD_REMOTE_SERVER=false` reuses the one already on the host; `nomusl`/`nocompress` work as upstream. To test the release download path from a dev build, `ZED_RELEASE_CHANNEL=stable ZED_BUILD_REMOTE_SERVER=never` (needs a published release with the assets).
- Checked live against a second Mac over SSH (Tailscale) with the dev app uploading the fork's server: the project opened (title "<host>  <folder>"), the project panel listed the files, a file opened, project search found matches in both files, and a terminal opened in the folder on that host. The first connection timed out while the 440 MB debug server cold-started there; the next attempt connected in 2 s. An agent tab in that project fails until the host has the `icarus` CLI.

**Terminal leftovers: tasks on the server, pane titles, history fallback, kitty keys, the CLI on SSH hosts:**
- **Task terminals on the server:** a task the user starts (tasks.json, `task: spawn`, rerun) in an Icarus workspace runs as a server terminal (`terminal.create` with `task: true`, the task's label, its command and the environment Zed resolved), shown with `icarus terminal attach`, which exits with the task's code. Zed's task UI stays: status, exit code, the rerun button, and waiting for the previous run unless concurrent runs are allowed. A rerun that replaces the tab's terminal, or closing the tab, kills the server one; quitting the app leaves it running, and its tab comes back attached while it runs (a finished task's tab isn't restored). `icarus terminal list` shows it as `task: <label>`; `terminal.info` has `task`. Only user tasks route (`Project::create_user_terminal_task`, used by the terminal panel): agent (ACP) and debugger terminals stay local, since they stop their command by killing the local process. An unreachable server runs the task locally as before.
- **Pane titles:** a server terminal's tab now shows its program's own title (OSC 0/2, carried in the server's snapshot so a reattached tab has it) over "folder — zsh", and a label wins over both. `icarus::SetPaneTitle` (Orca's Set Title…, through Zed's rename field) and `icarus::ClearPaneTitle` set the label on the server, as does the new `icarus terminal rename <id> [title]`; the server tells every client (`terminal.label`), so every tab showing that terminal follows. No default keys, as in Orca. Each Zed pane has its own tab bar, so split panes always show their own title.
- **Equalize:** Zed's `workspace::ResetPaneSizes` is the action; Orca binds no key to it either. The keybindings importer maps `terminal.equalizePaneSizes`, `terminal.setTitle`, `terminal.clearPaneTitle` and `worktree.history.back/forward` (to `pane::GoBack/GoForward`, without unbinding ⌥⌘←/→).
- **⌥⌘←/→ with a single tab group** go back/forward in the pane's navigation history, as Orca falls back to its history when there is no group to move to; with several groups they only move focus, and do nothing at the edge.
- **Kitty-keyboard-aware line editing:** the server's emulator tracks the kitty keyboard flags (push, pop, set; kept in snapshots and handoffs), reports them as `kitty_keyboard_flags` in `terminal.info` and tells every client (`terminal.keyboard`). The app adds `kitty_keyboard` to that terminal's key context, where ⌥⌫ sends `CSI 127;3u`, ⌥←/→ `CSI 1;3D/C` and ⌥⌦ `CSI 3;3~` (Linux: Ctrl+←/→ and Alt+Backspace) as xterm.js would, instead of the readline translations. The server still doesn't answer a program's `CSI ? u` query, since the app encodes other keys the legacy way, so this helps programs that push the flags without asking first.
- **The `icarus` CLI on SSH hosts:** an agent tab in a project opened over SSH looks for `icarus` on the host (PATH, the login shell's PATH, `~/.icarus/bin`). If it's missing, the app asks "Install Icarus on <host>?" and installs the release matching its own Icarus version (`icarus-<version>-<target>.tar.gz`, checked against the release's `SHA256SUMS`) into `~/.icarus/bin`: downloaded on the host with curl or wget, else downloaded by the app and sent over SSH. The tab then starts the host's server if needed (`icarus server start`) and runs `icarus acp`, so a host with the CLI but no running server works too. `ICARUS_RELEASE_BASE_URL` points it at another release location (tests, mirrors).

**Terminal and setup leftovers: kitty keys, attach snapshots, tab colours, always trust, issue command, environment recipes** (features.md §2.1, §2.5):
- **Full kitty keyboard encoding:** a server terminal whose program turned the protocol on gets every key in its encoding (the flags the server reports): Escape is `CSI 27u`; Ctrl, Alt and ⌘ (super) keys, and modified Enter, Tab and Backspace, are `CSI code;mods u`; modified cursor and function keys use kitty's forms (F3 is `CSI 13~`, F13–F35 the private-use numbers); "report all keys" turns typed text into escapes too, with alternate (shifted) keys and associated text when asked. Unmodified Enter/Tab/Backspace/arrows keep their legacy bytes, and ⌥ still types its character on macOS unless it's Meta. Only key presses are reported. So the server now answers `CSI ? u` with the current flags, and programs that ask before pushing get the untranslated keys as well. The encoder is `terminal::mappings::kitty`; the app hands each routed tab's flags over through a new `ExternalKeyboardFlags` hook.
- **Attach snapshots:** a snapshot leaves out the blank rows under the cursor (they scrolled a shorter window and pushed the screen into its scrollback, so a new terminal's first screen sat lower until the program redrew), `icarus terminal attach` sizes the server terminal to its window before asking for the snapshot, and its first attach asks for an inline snapshot (`terminal.attach { inline: true }`): no clearing, the cursor placed relatively, so lines the app wrote above it (Zed's "⏵ Task …" lines) stay.
- **`defaultTabs` colours:** `color` (`#rgb` / `#rrggbb`, as Orca validates it) is kept on the server terminal (`terminal.create { color }`, `terminal.info.color`, survives restarts and handoffs) and shown as a small dot in the terminal's tab (`ExternalTabColor` hook). A colour-only tab is kept, as in Orca.
- **Always trust:** Orca's "Always trust" per repository: every committed script (setup, archive, default tab commands, issue command, recipes) runs, including later changes, until `icarus project untrust <id>` (which clears it with the per-script approvals). `project.trust { always }`, `icarus project trust <id> --always`, `workspace.create { trust: "always" }` / `--always-trust`; `project.scripts` reports `always_trusted`. The app's trust prompt has an "Always trust scripts from …" checkbox.
- **`issueCommand`:** read from the primary checkout as Orca does: `.orca/issue-command` (the user's own, no trust needed; `project.hooks.issueCommand` in local or user settings works too), else `orca.yaml`'s `issueCommand` (trusted like the other scripts, kind `issue_command`). `{{artifact_url}}` and `{{issue}}` are filled in. It runs for a workspace linked to a GitHub item (a pull request start point, or a GitHub issue URL via `icarus workspace create --from-issue <url>`; Linear issues don't, as in Orca) in its own "Issue command" server terminal added to the layout beside the agent, without waiting for setup. An untrusted one doesn't run and the create says why in `warnings`; `issue_command: false` / `--no-issue-command` skips it. The app's trust prompt lists it for a pull request start.
- **Environment recipes (`environmentRecipes`, Orca's Cloud VM):** parsed with Orca's rules and messages (ids, duplicates, `command`/`cleanup` aliases, `destroy: none`, `checkoutMode`), trusted as a whole in Orca's trust-content form. The local server runs `create` / `suspend` / `resume` / `destroy` in the repository through the shell in their own process group with Orca's `ORCA_VM_*`, `ORCA_RECIPE_*`, `ORCA_REPO_*` variables (plus `ICARUS_` twins), lifecycle commands getting Orca's JSON payload on stdin; results are checked as Orca does (schema 1/2, provisioned-root only when both sides say so, absolute `projectRoot`). A connection is an Icarus server (`type: icarus-server`, Orca's `orca-server` accepted, `pairingCode` = `icarus://pair?address=HOST:PORT&code=CODE[&fingerprint=…]`) or SSH (`configHost`, or `user@host` on port 22). `icarus workspace create --recipe <id>` runs the recipe, pairs and saves the server as `env-<name>`, adds `projectRoot` there and creates the workspace on it (provisioned-root: the checkout itself, no worktree); a failure after the create destroys the environment again. `icarus recipe list|envs|suspend|resume|destroy` (resume re-pairs when the server moved; destroy forgets the saved server). RPCs `recipe.list|create|bind|environments|suspend|resume|destroy`.

## CI

`.github/workflows/app.yml` tests the app on every push to main and every PR that touches `app/**`, the three crates it pulls from the root workspace (`icarus-client`, `icarus-protocol`, `icarus-settings`) or the root `Cargo.toml`, and on demand via workflow_dispatch. Four parallel jobs on free hosted runners: `cargo test` for icarus_ui, title_bar, agent_ui, git_ui, project_panel and `workspace --lib` on Linux; the whole `zed` crate under nextest with two retries for upstream's timing-sensitive session-restore tests, also on Linux; clippy with `-D warnings` on icarus_ui, agent_ui, workspace, title_bar and zed (all targets) on macOS so the `cfg(target_os = "macos")` code is linted; and the Icarus visual tests (`ICARUS_VISUAL_ONLY=1`) on macOS, which compare against the tracked `icarus_*.png` baselines and upload the screenshots and diffs when they fail. The macos-15 image's Xcode ships the Metal compiler, so no extra toolchain or `runtime_shaders` is needed. Builds use `CARGO_PROFILE_DEV_DEBUG=0` and no incremental, caches are per job and saved only from main, and no disk cleanup is done because a build peaks under 20 GB on runners with 45+ GB free. The runner pins the theme mode to dark, so the baselines don't depend on the runner's system appearance.
